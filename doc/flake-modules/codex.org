#+title: codex

* Overview

~codex~ is a ~flake-parts~ module for projects that use the Codex CLI.

It helps you do three things from one place:

- write ~.codex/config.toml~ from Nix values;
- link project documentation and skills into ~.agents/~;
- expose reusable skill definitions to other flakes.

The module is configured under ~perSystem.codex~. In addition to the
project files it manages locally, it also exports ~skills.${system}~ at
the flake output level so that another flake can reuse the same skill
set.


* Installation

If your flake already imports this repository as an input and exports
~flakeModules.codex~, add it to ~imports~ in the usual ~flake-parts~ style:

#+begin_src nix
  {
    inputs = {
      flake-parts.url = "github:hercules-ci/flake-parts";
      infix.url = "git+https://codeberg.org/bingshan/infix.git?ref=main";
    };

    outputs =
      inputs@{ flake-parts, infix, ... }:
      flake-parts.lib.mkFlake { inherit inputs; } {
        imports = [
          infix.flakeModules.codex
        ];

        systems = [
          "x86_64-linux"
        ];
      };
  }
#+end_src

After that, configure the module under ~perSystem.codex~.


* Quick Start

The smallest useful configuration enables the module and provides
Codex settings:

#+begin_src nix
  {
    perSystem =
      { ... }:
      {
        codex = {
          enable = true;

          settings = {
            approval_policy = "on-request";
            model = "gpt-5.4";
            sandbox_mode = "workspace-write";
          };
        };
      };
  }
#+end_src

With this configuration, the module will:

- install the Codex CLI into the target development shell;
- write ~.codex/config.toml~ in the project root;
- leave ~.agents/docs~, ~.agents/README.md~, and ~.agents/skills/~ untouched
  unless you configure them explicitly.


* Example

The following example configures documentation, one MCP server, and
one skill:

#+begin_src nix
  {
    perSystem =
      { pkgs, ... }:
      {
        codex = {
          enable = true;

          readme = {
            file = ./agents/readme.md;
            path = ".agents/README.md";
          };

          docs.directory = ./agents/docs;

          mcp.nixos = {
            package = pkgs.mcp-nixos;
            settings = {
              command = "mcp-nixos";
              required = false;
              startup_timeout_sec = 20;
              tool_timeout_sec = 120;
            };
          };

          settings = {
            approval_policy = "on-request";
            model = "gpt-5.4";
            model_provider = "openai";
            sandbox_mode = "workspace-write";
            web_search = "cached";
          };

          skills.commit = {
            directory = ./agents/skills/commit;
            packages = with pkgs; [ git ];
          };
        };
      };
  }
#+end_src

This configuration produces the following user-visible effects:

- ~.codex/config.toml~ is written from ~codex.settings~.
- ~./agents/readme.md~ is linked to ~.agents/README.md~.
- ~./agents/docs~ is linked to ~.agents/docs~.
- ~./agents/skills/commit~ is linked to ~.agents/skills/commit~.
- ~pkgs.mcp-nixos~ is installed into the target development shell.
- ~pkgs.git~ is installed because the ~commit~ skill declares it as a
  runtime dependency.


* Reusing Skills From Another Flake

The module exports skills at ~skills.${system}~. Each entry has the same
shape as a local ~codex.skills.<name>~ entry:

- ~directory~ is a Nix store path that points to the exported skill
  directory;
- ~packages~ is the list of packages needed by that skill.

Another flake can reuse the exported definitions directly:

#+begin_src nix
  {
    perSystem =
      { pkgs, ... }:
      {
        codex = {
          enable = true;

          skills = inputs.infix.skills.${pkgs.system} // {
            local = {
              directory = ./agents/skills/local;
              packages = with pkgs; [ jq ];
            };
          };
        };
      };
  }
#+end_src

Use ~.${pkgs.system}~ when reading exported skills, because the package
list is system-specific.


* What The Module Manages

When ~perSystem.codex.enable = true~, the module can manage the
following project files and shell dependencies:

- ~.codex/config.toml~, written from ~codex.settings~.
- ~codex.readme.path~, linked from ~codex.readme.file~ when configured.
- ~.agents/docs~, linked from ~codex.docs.directory~ when configured.
- ~.agents/skills/<name>~, linked from ~codex.skills.<name>.directory~.
- the Codex CLI package in the selected development shell.
- MCP server packages declared under ~codex.mcp~.
- skill runtime packages declared under ~codex.skills.<name>.packages~.

The module also exports:

- ~skills.${system}~, a reusable set of skill definitions for downstream
  flakes.


* Option Reference

** ~perSystem.codex~

Main configuration entry for the module.

*** ~perSystem.codex.enable~

Type: ~Bool~.

Enables project file generation and shell integration.

Default: ~false~.

*** ~perSystem.codex.package~

Type: ~Maybe Package~.

Codex CLI package to install in the target shell. When unset, the
module uses ~pkgs.codex~.

Default: ~null~.

*** ~perSystem.codex.devshellName~

Type: ~String~.

Name of the development shell that receives the generated files,
packages, and shell initialization steps.

Default: ~"default"~.

*** ~perSystem.codex.mcp~

Type: ~AttrSet String Any~.

Named MCP server definitions. Each entry can contribute one package
and one settings attrset.

** ~perSystem.codex.mcp~

Each attribute under ~perSystem.codex.mcp~ defines one MCP server.

*** ~perSystem.codex.mcp.<name>.package~

Type: ~Maybe Package~.

Package to install in the target shell.

Default: ~null~.

*** ~perSystem.codex.mcp.<name>.settings~

Type: ~AttrSet String Any~.

Settings merged into ~mcp_servers.<name>~ in the generated Codex config.

Default: ~{ }~.

When the same server name appears both in ~codex.settings.mcp_servers~
and in ~codex.mcp~, the values from ~codex.mcp.<name>.settings~ are merged
into the final configuration.

** ~perSystem.codex.readme~

Type: ~AttrSet String Any~.

README link configuration.

*** ~perSystem.codex.readme.file~

Type: ~Maybe Path~.

Source file to link into the project.

Default: ~null~.

*** ~perSystem.codex.readme.path~

Type: ~String~.

Relative destination path inside the project.

Default: ~".agents/AGENTS.md"~.

If ~file~ is ~null~, the module does not create the link. If the
destination is already a symbolic link, it is removed when the shell
starts.

** ~perSystem.codex.docs~

Type: ~AttrSet String Any~.

Documentation directory link configuration.

*** ~perSystem.codex.docs.directory~

Type: ~Maybe Path~.

Source directory to link as ~.agents/docs~.

Default: ~null~.

** ~perSystem.codex.settings~

Type: ~AttrSet String Any~.

Free-form configuration written to ~.codex/config.toml~.

Before writing the file, the module adjusts the value in two ways:

- it ensures that ~project_doc_fallback_filenames~ includes
  ~codex.readme.path~;
- it merges MCP server settings from ~codex.mcp~ into ~mcp_servers~.

The module also removes recursive ~null~ values before writing the file.

** ~perSystem.codex.skills~

Type: ~AttrSet String Any~.

Each attribute under ~perSystem.codex.skills~ defines one skill.

*** ~perSystem.codex.skills.<name>.directory~

Type: ~Path~.

Source directory for the skill. It is linked into
~.agents/skills/<name>~.

*** ~perSystem.codex.skills.<name>.packages~

Type: ~[Package]~.

Packages that should be available when the skill runs.

Default: ~[ ]~.

All skill packages are collected and added to the selected development
shell.


* Exported Output

In addition to the local project integration, the module exports
~skills.${system}~.

For each skill name:

- the exported ~directory~ points to a path in the Nix store;
- the exported ~packages~ list is preserved;
- the exported value can be reused directly by another flake.

This export does not depend on ~codex.enable~. If you define
~perSystem.codex.skills~, the corresponding ~skills.${system}~ output is
still available even when local file generation is disabled.


* Behavior Notes

** Generated documentation paths

If ~codex.settings.project_doc_fallback_filenames~ contains paths inside
a directory that does not yet exist, the module creates the parent
directories before linking files into place.

** Skill links

At shell startup, the module updates ~.agents/skills/~ as follows:

- it creates links for all configured skills;
- it removes symbolic links that no longer correspond to configured
  skills;
- it leaves non-symbolic-link files in that directory unchanged.

** Default package selection

If you do not set ~codex.package~, the module installs ~pkgs.codex~.


* Repository Example

This repository exports a ~commit~ skill, so another flake can
reference:

#+begin_src nix
inputs.infix.skills.${pkgs.system}.commit
#+end_src

That value contains:

- a ~directory~ path in the Nix store;
- the ~packages~ required by the ~commit~ skill.
